개요

대학원 수업 팀 프로젝트로 나들이봄이라는 웹 프로토타입을 만들고 있습니다. 아이 성향에 맞춘 하루 나들이를, 화장실·주차·수유실 같은 설비 정보와 함께 설계해 주는 서비스입니다.

이 글은 그 프로젝트를 AI 코딩 에이전트와 함께 진행한 순서를 정리한 것입니다. 핵심은 한 줄입니다.

코드부터 시키지 않습니다. 기획 문서를 먼저 만들고, 그 문서를 읽게 한 뒤 코드를 시킵니다.

전체 흐름은 아래 그림과 같습니다. 그림은 one-page-diagrams 스킬로 만들었고, 만드는 과정은 글 끝에 적었습니다.

단계별 프롬프트는 다른 프로젝트에 옮겨 쓸 수 있게 일반화해서 적었습니다. { } 안은 자기 프로젝트 내용으로 바꾸면 됩니다.

폴더 구조부터 정합니다

문서와 코드를 한 저장소에 둡니다. 에이전트가 문서를 읽고 코드를 쓰기 때문입니다.

app/
├── docs/                 # 기획 문서 7개
│   ├── worldview.md
│   ├── brand.md
│   ├── customer-journey.md
│   ├── business-canvas.md
│   ├── PRD.md
│   ├── plan.md
│   └── free-apis.md
└── web/                  # 프로토타입 (HTML · CSS · JS)

1단계. 문제 발견

재료는 사람이 모읍니다. 이 프로젝트에서는 데스크리서치, 경쟁 앱 4종 벤치마킹, FGD(표적집단토의) 결과 보고서가 재료였습니다. AI에게는 정리를 맡깁니다.

첨부한 FGD 결과 보고서와 경쟁 앱 화면 4장을 읽고 정리해줘.
- 참가자가 반복해서 말한 불편(Pain Point)을 근거 문장과 함께 표로
- 경쟁 앱이 제공하지 않는 정보
- 보고서에 없는 내용은 추측하지 말고 [확인 필요]라고 적어줘

마지막 줄이 중요합니다. 넣지 않으면 그럴듯한 수치가 섞여 들어옵니다.

2단계. 세계관과 브랜드

기능보다 먼저 “무엇을 믿고, 무엇을 하지 않을지"를 문서로 만듭니다. 나중에 화면 문구와 디자인을 정할 때 기준이 됩니다.

1단계 정리를 바탕으로 docs/worldview.md를 써줘.
구성: 우리가 믿는 것 / 서비스가 바라보는 세상 / 톤앤매너 원칙 / 장기 비전 / 하지 않을 것
각 항목은 3~4줄. 과장 표현("최고의", "완벽한")은 쓰지 마.

docs/worldview.md를 읽고 docs/brand.md를 써줘.
구성: 브랜드명 후보 3~4개 / 슬로건 / 톤보이스 / 컬러 팔레트(HEX, 용도) / 타이포그래피 / 핵심 메시지
팀이 정해야 하는 항목에는 [의사결정 필요]를 붙여줘.

나들이봄의 세계관 문서에는 “하지 않을 것"이 세 줄 있습니다. 그중 하나가 “단순 장소 나열·검색 중심 서비스로 회귀하지 않는다"입니다. 기능을 추가할지 고민될 때 이 줄이 판단 기준이 됩니다.

3단계. 고객여정맵과 비즈니스 캔버스

FGD 정리와 docs/worldview.md를 읽고 docs/customer-journey.md를 표로 써줘.
열: 단계 / 고객 행동 / Pain Point / Needs / 감정 변화
회원가입과 리뷰 작성은 필수 단계로 넣어줘. 표 아래에 근거 자료와 설계 반영 포인트를 적어줘.

docs/customer-journey.md를 읽고 docs/business-canvas.md를 9블록 표로 써줘.
수익 가정은 계산식을 보여 주고 "가정치, 검증 필요"라고 표시해줘.
핵심 리스크와 [의사결정 필요] 항목도 따로 적어줘.

여정맵은 7단계(인지 → 회원가입 → 추천 탐색 → 일정 설계 → 방문 → 리뷰 작성 → 재방문)로 나왔습니다. 이 단계가 나중에 화면 구성의 뼈대가 됐습니다. 홈·장소·일정·마이 네 개의 하단 탭이 여정 단계와 거의 1:1로 맞습니다.

4단계. PRD와 구현 계획

여기까지 오면 코드를 쓸 준비가 됩니다. PRD에는 비목표와 수용 기준을 꼭 넣습니다.

docs/ 아래 문서를 모두 읽고 docs/PRD.md를 써줘. 범위는 수업용 웹 프로토타입이야.
구성: 개요 / 배경·문제 정의 / 목표 / 비목표 / 사용자 스토리와 수용 기준(화면별) / 데이터 모델
수용 기준은 "~하면 ~가 보인다"처럼 확인할 수 있는 문장으로 써줘.

docs/PRD.md를 읽고 docs/plan.md를 써줘.
구성: 파일 구조 / 개발 순서(번호) / 테스트 체크리스트 / 향후 확장 / 의사결정 필요사항 표

비목표가 없으면 에이전트가 결제, 이메일 인증, 지도 연동까지 만들려고 합니다. 나들이봄 PRD는 “실제 결제, 실제 이메일 인증, 서버 측 인증은 구현하지 않는다"를 비목표로 적어 두었습니다.

plan.md의 의사결정 표는 이렇게 생겼습니다. 정해진 것과 안 정해진 것이 한눈에 보입니다.

항목상태
브랜드명확정: 나들이봄
핵심 메시지확정: “가서 당황할 일 없는 하루”
초기 집중 권역미확정
리워드 형태미확정
수익 모델 우선순위미확정

5단계. 프로토타입 개발

프레임워크와 빌드 도구 없이 순수 HTML·CSS·JS로 만들었습니다. 회원·세션·일정은 브라우저 localStorage에 저장합니다. 화면은 11개입니다.

한 번에 다 시키지 않고 plan.md의 개발 순서대로 끊어서 시킵니다.

docs/PRD.md와 docs/plan.md를 읽고 개발 순서 1~3번만 구현해줘.
(시드 데이터, 공통 app.js, 회원가입·로그인)
끝나면 PRD 5.1, 5.2의 수용 기준을 하나씩 확인해서 결과를 표로 알려줘.

개발 순서 4번(홈, 장소 목록, 장소 상세)을 구현해줘.
색과 글꼴은 docs/brand.md를 따르고, 화면 문구는 docs/worldview.md의 톤앤매너 원칙을 지켜줘.

디자인은 시안을 여러 개 받아서 고릅니다.

홈 화면 디자인 시안을 4개 만들어줘. 각각 별도 HTML 파일로, 같은 데이터를 쓰게 해줘.
refer_images/ 폴더의 경쟁 앱 화면을 참고하되 그대로 따라 하지는 마.

네 개를 나란히 열어 보고 시안 4를 골랐습니다. 고른 뒤에는 그 결정을 문서에 다시 적게 합니다.

시안 4로 확정했어. 전체 화면에 적용하고, docs/brand.md와 docs/plan.md의 의사결정 표를 갱신해줘.

코드와 문서가 어긋나지 않게 하는 것이 요령입니다. 결정이 바뀌면 문서부터 고칩니다.

6단계. 공유 데이터 연결

localStorage만 쓰면 내가 쓴 리뷰가 다른 사람 브라우저에서는 보이지 않습니다. “리뷰가 쌓인다"를 팀원과 방문자에게 보여 주려면 공유 저장소가 필요합니다. 그래서 리뷰, 사진, 기획 문서만 Supabase로 옮겼습니다.

데이터저장 위치
회원, 세션, 일정브라우저 localStorage
리뷰Supabase 테이블
리뷰 사진, 문서 이미지Supabase Storage
기획 문서 본문Supabase 테이블 (.md 파일은 백업)
리뷰만 Supabase로 옮겨줘. 회원·세션·일정은 localStorage 그대로 둬.
- reviews 테이블 스키마와 RLS 정책 SQL을 먼저 보여줘. 내가 실행할게.
- 사진은 Storage 버킷에 올리고 공개 URL을 리뷰에 저장
- 바꾼 내용을 docs/PRD.md의 데이터 모델과 비목표에 반영해줘

SQL은 사람이 읽고 직접 실행합니다. 키는 채팅에 붙이지 않고 설정 파일에 직접 넣습니다. 브라우저에 공개되는 키만 쓰고, 관리자 키는 저장소에 넣지 않습니다.

7단계. 체크리스트 통과 후 배포

plan.md의 테스트 체크리스트는 12개 항목입니다. 몇 가지만 옮기면 이렇습니다.

  • 회원가입 → 자동 로그인 → 홈 이동
  • 비로그인 상태로 내부 페이지에 직접 접근하면 로그인으로 이동
  • 리뷰 작성 시 체크리스트를 채우지 않으면 제출 차단
  • 다른 브라우저로 로그인해도 방금 쓴 리뷰가 보이는지
  • 모바일 너비(375px)에서 레이아웃이 깨지지 않는지
docs/plan.md의 테스트 체크리스트를 브라우저에서 하나씩 실행해 보고 결과를 표로 알려줘.
통과하지 못한 항목은 원인과 고칠 파일을 적어줘. 고치는 건 내가 확인한 뒤에 해.

통과하지 못한 항목이 있으면 5단계로 돌아갑니다. 순서도에서 오른쪽으로 돌아가는 선이 이 부분입니다. 실제로 리뷰 저장을 비동기로 바꾼 뒤 닫는 괄호 하나가 남아 장소 상세 화면이 깨진 적이 있습니다. 커밋 기록에 그 수정이 남아 있습니다.

코드는 GitHub 저장소에 올리고 Vercel로 배포했습니다. 빌드 과정이 없는 정적 파일이라 설정할 것이 거의 없습니다.

배포용 저장소에 올릴 README.md를 써줘.
서비스 한 줄 소개, 기획 문서 목록, 기술 스택, 데이터가 어디에 저장되는지를 적어줘.

첫 커밋 이후 지금까지 28번 커밋했습니다. 고칠 때마다 작게 커밋해 두면 되돌리기 쉽습니다.

순서도는 이렇게 만들었습니다

글 맨 위의 순서도는 프로젝트에 설치한 one-page-diagrams 스킬로 만들었습니다. 요청은 이런 식으로 하면 됩니다.

docs/ 문서와 저장소 기록을 읽고, 이 프로젝트의 기획부터 배포까지 흐름을 순서도로 그려줘. PNG도.
  • 스킬이 “분기가 있는 순서도"로 판단해 SVG 방식을 골랐습니다.
  • 그림 속 내용은 문서에 있는 것만 들어갔습니다. 화면 11개, 여정 7단계, 경쟁 앱 4종 모두 문서에 적힌 값입니다.
  • 초안은 세로형으로 나왔고, 블로그에는 세로형이 맞아서 그대로 썼습니다. 슬라이드에 넣을 때는 “가로형으로"라고 하면 다시 만들어 줍니다.

설치 방법은 실습 글에 있습니다.

정리

단계산출물프롬프트의 요점
1. 문제 발견Pain Point 정리없는 내용은 [확인 필요]
2. 세계관 · 브랜드worldview.md, brand.md“하지 않을 것"을 적게 한다
3. 여정맵 · 캔버스customer-journey.md, business-canvas.md가정치는 가정치라고 표시
4. PRD · 계획PRD.md, plan.md비목표와 수용 기준
5. 개발HTML · CSS · JS개발 순서대로 끊어서
6. 공유 데이터SupabaseSQL은 사람이 읽고 실행
7. 검사 · 배포체크리스트, README통과 못 하면 5단계로
  • 문서가 먼저입니다. 에이전트는 문서를 읽은 만큼만 일관되게 만듭니다.
  • 결정이 바뀌면 문서를 먼저 고칩니다.
  • 정하지 못한 것은 [의사결정 필요]로 남겨 둡니다. 비워 두면 에이전트가 대신 정합니다.

Building an app with an AI agent: prompts from planning to deployment (English)

Overview

Notes from a graduate-course team project: a web prototype called Nadeuri-bom, which plans a day out with kids using verified facility information. The rule that held the project together was simple: write the planning documents first, then let the agent read them before it writes code.

Flow

  1. Find the problem — desk research, four competitor apps, a focus group report. Ask the agent to summarize and to mark anything missing as “needs checking”.
  2. Worldview and brand — what we believe, what we will not do, tone, colors.
  3. Customer journey and business canvas — seven journey stages, value proposition, revenue.
  4. PRD and plan — goals, non-goals, acceptance criteria, build order, test checklist.
  5. Prototype — plain HTML, CSS and JS, eleven screens, localStorage. Build in the order the plan lists.
  6. Shared data — move reviews, photos and planning docs to Supabase. Read and run the SQL yourself.
  7. Checklist, then deploy — run the test checklist; failures go back to step 5. Deploy the GitHub repository to Vercel.

Takeaways

  • Documents first. The agent stays consistent only as far as the documents go.
  • When a decision changes, update the document before the code.
  • Leave undecided items marked as open; otherwise the agent decides for you.
